### 1.3 The decisions of 5 October 2026

On 5 October 2026 the owner dropped the mailing list, so that people's replies and requests reach the project by one route, and asked for the plan to go ahead without it. D4: the network-free reminders (layer 3) are dropped. D14: help through GitHub Issues only. Every other decision as recommended, except D17 and D18, which were settled later the same day with D19 to D21 (below).

What this changes:
- **No mailing list.** Layer 5 is dropped: no JISCMail list, no sign-up links, no emails. Researchers hear of new versions only through Exegete itself. The README, with its new section "Keeping Exegete up to date", and the release notes remain for anyone who looks; the README no longer suggests watching the repository's Releases on GitHub.
- **No network-free reminders (D4).** There is no reminder when checking is off, and none when checking keeps failing. The new-version notice is the only way Exegete tells researchers of a new version.
- **Help through GitHub Issues only (D14).** This was already the policy.
- **Every other decision as recommended** (section 12).

**The consequence, stated plainly.** Two groups will now never be told that a new version exists:
- researchers whose checking is off: those who switch it off in the extension, and those on the Terminal route who never switch it on, since it is off there by default (D1);
- researchers whose network blocks the check (for example a university proxy that inspects encrypted traffic).

They can still ask "Is Exegete up to date?" (except in the `core` tool set, which has no check tool, D5), but with checking off that answer makes no connection, and behind a blocking network it can only say that it could not check. The same applies to everyone on 0.14.1 or earlier, since their copy has no check.

## 2. What a researcher experiences

The main case is a researcher using Claude Desktop's chat with the extension. It follows the decisions recorded in section 12: D1 option (c), D2, D3, D4 (none), D5, D10 option (a), D11, D12, D19 and D20. It describes what the build in nicotem/exegete#11 does; that pull request is not yet merged or released. The website it fetches from, with the version file and the "Install or update Exegete" page, is not yet published (section 4), so until it is, a check can only end as "could not check".

1. **At installation or update**, the extension's settings show a third item, "Tell me when a new version is out", switched on by default (D1; packaging/desktop-extension/manifest.in.json, `user_config.update_check`). Two things are still to be verified on a real computer: whether Claude's installation screen shows it (section 13, item 4), and whether an update gives an existing installation this default (item 2). Exegete itself reads an unset, empty or unsubstituted value as on in the extension (`updates.read_setting`).
2. **The first time Exegete runs on this computer with checking on** (that is, while no disclosure is recorded here), the first successful answer of an Exegete tool other than the check tool carries a one-time note for Claude to pass on, as the answer's last field, `exegete_notice`. It says that Exegete can now check for new versions, what that sends, how to switch it off, and that its first check will be on or after a date seven days away. Nothing connects before that date, the check tool included. This applies to a new installation and to an update from 0.14.1 or earlier alike, but only while the setting is on (section 3.5). It never goes on a refusal. If the check tool is asked first, its own message tells the researcher what the check does and sends, how to switch it off and the date of the first check, and the note is not given again. A start that gives no successful answer leaves the note due for the next one.
3. **From then on, at most once a week**, when Claude starts Exegete (or, for an Exegete left running for weeks, during use), Exegete fetches a small file from its website. This runs in the background with an overall time limit, so it does not hold up Exegete's work. If the computer is offline or a firewall blocks it, nothing is said in the conversation (section 1.3 states the consequence); one line in the log names the kind of failure.
4. **When a newer version exists**, the next successful answer of an Exegete tool other than the check tool carries a short note for Claude to pass on, once. The server cannot tell conversations apart, so it is whichever conversation calls Exegete next. An answer carries one note at most, and a disclosure or after-update note still due goes first. The note gives the new version and its date, the version they have, whether it is important (in fixed, calm words), and the update page, which is to say what changed (the page is not yet published; section 4.3). It ends: To update, they can ask: "How do I update Exegete?" In the `core` tool set it ends instead with "To update, see" and the update page's address. It is not repeated for that version, by this copy or by any other copy of Exegete on the computer: the record is kept in the state file they share. If that file cannot be written, the record lasts only until Exegete restarts, and two copies writing at the same instant can, at worst, repeat it once. If the researcher has already learnt of that version by asking, no note follows.
5. **The researcher asks** "How do I update Exegete?" or "Is Exegete up to date?". In the asking modes, Claude asks permission to run the check, as it does for Exegete's writing tools; in auto modes a classifier or reviewer decides, as it does for those tools (D11). Exegete answers with a message to pass on, and:
   - the version they have and its date;
   - the newest version, its date and whether it is important;
   - when a newer version exists, steps for their computer (in the extension, with a direct download link) and the release notes link;
   - the update page.

   Asked twice within a day, it fetches once; if a check is already running, it waits for that one and uses its result. Section 3.6 lists the answer's fields.
6. **They update.** They download the file, open it, click Install, then quit and reopen Claude Desktop. The update page is to show each step with pictures. It is not yet made, and its screenshots need a real Mac and a real Windows computer (section 4.3).
7. **In the first successful answer of an Exegete tool other than the check tool after the update**, Exegete says once that it was updated, so the update worked, what is new, and where the full release notes are. The words come from src/exegete/release.py (`SUMMARY`), written when the release is prepared and never fetched; the link is built from the version. A restart before any such answer leaves the note due. On an update from 0.14.1 or earlier with checking on, the disclosure note of step 2 takes its place. (D19: kept.)

**With checking switched off**, Exegete makes no connection at all, including when asked (D2). The tool then says that it made no connection, and gives the installed version, its date (when release.py describes that version), the update page, and how to switch checking on: in the extension, the setting "Tell me when a new version is out"; on the Terminal route, `EXEGETE_UPDATE_CHECK` set to `on` (INSTALL.md, "Environment variables the server reads").

**On the Terminal route** (pip, pipx, uv tool, uvx, a copy of the source, or a copy started under the old name, qualcoder-mcp), whichever app starts Exegete (LM Studio, Codex, Claude Code), the setting is the environment variable `EXEGETE_UPDATE_CHECK`, which has one spelling only (section 3.7 gives its values). Under D1 it is off unless switched on (`updates.read_setting`), and while it is off the tool gives no commands (D2): it points to the update page, and says to set `EXEGETE_UPDATE_CHECK` to `on` to let Exegete check (INSTALL.md, "Environment variables the server reads").

Switched on, the tool gives three steps: quit the app that started Exegete; run the update in the computer's own shell (PowerShell on Windows, Terminal elsewhere); open the app again. For pip, pipx and uv tool the update is one command with the version pinned. A copy of the source, under either name, goes to its folder and runs `git fetch --tags`, then `git merge --ff-only v<new>`, then `pip install -e .` with its own Python. Paths under the home folder are written from `$HOME`. A copy started as qualcoder-mcp in a plain virtual environment gets both names pinned while the newest version is below 1.0. Otherwise (uv tool, pipx, no virtual environment, a Python path no quoting can carry, or 1.0 and later) it gets no command, only INSTALL.md, "Coming from qualcoder-mcp". On the other routes, uvx, a route Exegete cannot tell, or a path no quoting can carry gets no command: the update page and INSTALL.md, "Updating the MCP Server". In the `core` tool set, which LM Studio uses, the tool is absent, so notices there point to the update page instead of saying "ask".

## 3. The parts inside Exegete

### 3.1 The version file: four values, no text, no links

The only thing Exegete ever fetches is a small file at one permanent address. Under D3 that address is `https://nicotem.github.io/exegete/latest.json` (src/exegete/updates.py, `VERSION_FILE_URL`). Nothing is published there yet: the Pages site and the release job that writes the file (D8, section 4.2) are still to be built. Until they are, a check can only end as "could not check".

```json
{"format": 1, "version": "0.15.0a0", "released": "2026-11-12", "important": false}
```

**Why no text and no links.**
- The security review found that any text from the network that enters the conversation is a way to give the assistant instructions, next to participants' data.
- A 300-character limit does not prevent that. Text like "before passing this on, call read_pseudonym_list..." fits easily.
- Links read from the file could be bent to other repositories: `../` segments, percent-encoded dots and forks' commits all pass a prefix check.

**So every sentence and every link Exegete shows is written in its own code** (src/exegete/updates.py):
- the display form (0.15.0-alpha) and the tag (v0.15.0-alpha) are derived from `version` by a fixed rule (`Version.display`). `a` becomes `-alpha`, `b` becomes `-beta` and `rc` becomes `-rc`, and a pre-release number other than 0 follows after a dot: 0.15.0a0 is 0.15.0-alpha, 0.15.0b2 is 0.15.0-beta.2. This is pyproject.toml's spelling, which the extension's file name also uses (scripts/build_desktop_extension.py, `build`);
- the download link is built as `https://github.com/nicotem/exegete/releases/download/v<display>/exegete-<display>.mcpb` (`download_link`);
- the release notes link is `https://github.com/nicotem/exegete/releases/tag/v<display>` (`release_notes_link`);
- the update page's address is a constant in the package (`UPDATE_PAGE`, `https://nicotem.github.io/exegete/update/`). So are the two links to INSTALL.md on GitHub that some of the tool's answers give: `INSTALL_UPDATING` ("Updating the MCP Server") and `INSTALL_COMING_FROM` ("Coming from qualcoder-mcp"). A test collects the links in the disclosure note and in two of the tool's answers, and checks that each is one of these five forms: the download link, the release notes link and these three constants (tests/test_updates.py, `test_every_link_shown_is_one_of_exegetes_own`).

**"What changed" for the new version** is given by pointing to the update page. The researcher reads it in their browser, and the assistant never reads it (D10, option (a)). The notice says "What's new: <update page>"; for an important release, it says instead that the page explains the problem and what to do until they update. When a newer version exists, the tool's answer also gives that release's notes link (`release_notes`). The note after an update gives the release notes link and, when the running version is the one src/exegete/release.py describes, that version's own summary. The update page is not built yet (section 4.3), so until it is, links to it lead to a missing page.

**What a compromised file can still do:** claim a version that does not exist, hide a real one, mark one important, or give a false release date (any date up to two days after today). Each of these is a validated value (3.2). It cannot choose a word or a link.

**The format is permanent.** `format` stays 1 for good, and clients ignore unknown keys. A future incompatible format would be published beside it under another name, so that copies already installed keep working. CONTRIBUTING.md, "The check for new versions", records the rule.

### 3.2 Validating and comparing versions

The version ends up in commands that researchers paste into a terminal, so its validation is also the control against command injection.

- **`version`** must fullmatch, with `re.ASCII`: `(0|[1-9][0-9]{0,3})\.(0|[1-9][0-9]{0,3})\.(0|[1-9][0-9]{0,3})((a|b|rc)(0|[1-9][0-9]{0,3}))?`. Never use `\d`, `$` or `re.match` (src/exegete/updates.py, `_PUBLISHED` and `parse_published`).
- **`released`** must fullmatch `[0-9]{4}-[0-9]{2}-[0-9]{2}`, then pass `date.fromisoformat`. A date more than two days in the future is malformed; the two days are counted from today's UTC date (`parse_date`).
- **`format`** must satisfy `type(format) is int and format == 1`. **`important`** must satisfy `type(important) is bool`.
- **Any malformed value** refuses the whole file as "not the expected file" (`parse_version_file`; tests/test_updates.py, `TestTheVersionFile.test_anything_else_is_not_the_expected_file`). A version that carries a shell command is refused by `parse_published` (tests/test_updates.py, `TestVersions.test_the_version_file_names_only_plain_versions`).
- **The installed version** is parsed by the same number rule (`parse_installed`), whose pattern also allows a `.devN` suffix; the version file may not name one (`parse_published`). `0.0.0+unknown` (a source tree without install), a local part, or anything unparseable counts as "unknown": no note of any kind and no check. Asked with checking on, the tool makes no connection and says that it cannot tell which version this is (tests/test_updates.py, `test_an_unknown_version_gets_no_comparison`).
- **An installed `.devN` early build** ranks below its release.
- **What the tool says, by comparison:**
  - steps and notices only when newest > installed;
  - equal: `up_to_date` is true, and the answer says "You have the newest version of Exegete, <installed> (<date>). Exegete will tell you here when a newer one comes out." (the date only when this copy knows it);
  - newest < installed: `up_to_date` is also true, with no steps, and the answer says "You have <installed>, which is newer than the newest published version, <newest>. There is nothing to update." Exegete never gives steps that would install a lower version.
- **A test** compares the hand-written ordering with `packaging.Version` over a grid of generated versions, early builds included (tests/test_updates.py, `TestVersions.test_the_order_is_pep_440s`). Exegete itself does not use `packaging`: pyproject.toml does not name it, and it reaches the development environment through the dev extra's pytest, build and twine.

### 3.3 The check

**When it runs:**
- in a daemon thread (`exegete-weekly-check`) that `updates.start()` starts only when a check is due. `main()` calls `updates.start()` after `_settle_state_folder()` has returned and immediately before `mcp.run()` (src/exegete/server.py, `main()`). The call is guarded: if it fails, a warning is logged and the server starts without the check (tests/test_updates.py, `test_a_start_that_fails_never_stops_the_server`);
- never for `--version` or `--check-transition`, which promise to create nothing, nor when `main()` refuses to start the server, since it stops before the call. `updates.start()` writes nothing itself (tests/test_updates.py, `test_a_start_writes_nothing`): the version that runs is recorded after the first tool answer (`after_call`) or when a note is given (`mark_given`);
- only when the setting is on, the installed version is known (3.2), the disclosure has been given (3.5), seven days have passed since it was given (`first_check_after`; the note names that day, in the researcher's local time, as the first-check date), and the last **attempt** is at least seven days old, whether it succeeded or not (src/exegete/updates.py, `_check_due`). Gating on attempts, not successes, is what keeps "at most once a week" true behind a blocking network (tests/test_updates.py, `test_at_most_one_attempt_a_week_even_when_each_fails`);
- one fetch at a time in the process (`_FETCHING` and `check_now`): a background check that finds one running gives up, and an asked check waits for it (up to `DEADLINE` plus two seconds) and uses its result instead of fetching again (tests/test_updates.py, `test_an_asked_check_waits_for_a_running_one`);
- the time of each attempt and its result are also kept in memory for the run (`_Run.memory`), so when the state file cannot be written (a full disk, a Windows sharing violation) the weekly limit, the one-day reuse and the once-per-version notice still hold (tests/test_updates.py, `test_unwritable_state_still_checks_once_a_week`, which covers the first two; no test covers the notice with a file that cannot be written);
- also, for a server that stays running for weeks, from the tool-call hook (src/exegete/server.py, `_ExegeteMCP.call_tool`, through `updates.due_note`). The same conditions apply, and the check starts only once no disclosure or after-update note is waiting, never on a call to `check_for_updates` itself. It runs in a daemon thread, never blocks the call, and never starts while an earlier background check is still running.

**The fetch:**
- Python's standard library (`urllib.request`) with `ssl.create_default_context()`. No unverified context, no httpx and no bundled certificate file. Only `https` is allowed, except plain `http` to this computer itself (127.0.0.1, ::1, localhost), which the tests' own server uses; proxies are bypassed for it. Any other scheme, or a user name or password in the address, is refused as "address not allowed" (src/exegete/updates.py, `_opener`; tests/test_updates.py, `test_only_https_beyond_this_computer`).
- A test checks that the address in the source is the https one and that `ssl.create_default_context()` requires a certificate (`verify_mode` is `CERT_REQUIRED`) (tests/test_updates.py, `TestTheFetch.test_the_real_address_is_https_on_the_project_site`). It checks neither `check_hostname` nor the context the opener is given.
- One overall deadline of 8 seconds (`DEADLINE`), covering name lookup, connection, TLS and the whole read. It runs in a worker thread that is abandoned on timeout, because urllib's own timeout covers each socket step, not the whole fetch.
- No redirects: every 3xx is refused ("the website redirected").
- Exegete sets no `Accept-Encoding`; Python's http.client adds `Accept-Encoding: identity`, which asks for an uncompressed answer. Any `Content-Encoding` other than `identity` is refused as "not the expected file" (`_fetch_once`; tests/test_updates.py, `test_a_compressed_answer_is_refused`).
- At most 16,385 bytes are read, counted as read. The body is decoded as strict UTF-8. `json.loads` runs with NaN and Infinity refused and duplicate keys refused, and the top level must be an object. Any exception, `RecursionError` included, means "could not check".
- The request carries `User-Agent: Exegete` and, from Python's own library, `Host`, `Connection: close` and `Accept-Encoding: identity`, and nothing else: no version, no operating system, no identifier, no cookie. A test checks that the User-Agent is "Exegete", that no cookie is sent and that no header outside those four is sent (tests/test_updates.py, `TestTheFetch.test_it_reads_the_file_and_says_nothing_else`).
- Proxies: urllib reads the system proxy settings on macOS and Windows, but not PAC files. Claude Desktop passes no `HTTPS_PROXY` to the extension. Behind a TLS-inspecting university proxy whose certificate the uv-managed Python does not trust, the check fails quietly: nothing is said in the conversation, the log names the kind of failure only ("certificate not trusted"), and asking gives the could-not-check answer, naming the same kind (section 2, step 3; section 1.3). This is to be checked on a real computer (section 13, item 8).

**The log:**
- one line at every start, at INFO level: "Checking for new versions: on" or "Checking for new versions: off" (src/exegete/updates.py, `start`). Before it, an unrecognised value of `EXEGETE_UPDATE_CHECK` adds one warning: "EXEGETE_UPDATE_CHECK is not one of on, off, true, false, 1 or 0, so the check for new versions is off." This lets a researcher record the state as evidence for a data-management plan;
- after a failed attempt, one line at INFO level, "The check for new versions could not be made: <kind>", where the kind is one of eight fixed phrases (src/exegete/updates.py, the constants after `CheckFailed`: "no connection", "no answer in time", "certificate not trusted", "the website refused", "the website redirected", "not the expected file", "the answer was too large", "address not allowed"). It never gives the message or a proxy address. The tool's answer names the same kind;
- the project's `error_label` (src/exegete/database.py) is used only where the check could not start (src/exegete/server.py, `main()`) and where a note could not be worked out or added (`_ExegeteMCP.call_tool`). A state file that cannot be written is logged at debug level by the exception's type name only (`update_state`); `after_call` logs any other failure of its own the same way.

### 3.4 The state file

**Where it lives.** `preview_tokens.state_home() / "update_check.json"`, not a hard-coded `~/.exegete`. A run whose folder move failed uses `~/.qualcoder_mcp` (src/exegete/state_folder.py: `current()`, and the "rename failed" and "link failed, put back" outcomes of `move()`), and tests isolate the folder through `state_home()`.

**Why the order matters.** Nothing about updates is read or written before `_settle_state_folder()` returns. Writing first, on a computer updating straight from 0.14.0, would create `~/.exegete` before the one-time move. The move would then keep the preview-token key behind and make a new one. That key "also seals every pseudonymisation run record" (src/exegete/state_folder.py, module docstring). This is deterministic, not a race.

**How it is written and read:**
- written as the MRU hint is: `tempfile.mkstemp` (created exclusively, mode 0600) beside the file, then `os.replace`, and a failed write removes its temp file (src/exegete/server.py, `_open_mru_tmp` and `_remember_mru_project`; src/exegete/updates.py, `update_state`);
- read as the MRU hint is: binary, capped (16,384 bytes, `STATE_MAX_BYTES`), strict UTF-8, with NaN and Infinity refused; each value is checked when read, and anything malformed is treated as absent (src/exegete/server.py, `_mru_hint`; src/exegete/updates.py, `read_state`);
- the folder is made with `ensure_state_dir` (owner-only), and only when a record is written. The version that runs is recorded (`after_call`) only once the folder exists. With checking off nothing else is recorded, so the check never makes the folder: on a computer where Exegete never ran, it writes nothing until another part of Exegete has made the folder.

**What it holds:**
- `format`, always 1.
- `last_attempt`, whole seconds since the epoch, recorded whether the attempt succeeded or not. A value more than a day in the future is ignored, as for `disclosed_at` (`first_check_after` may be up to nine days ahead). A later attempt recorded by another copy is kept.
- `last_error`, the kind of the last failure (one of the eight fixed phrases, such as "no connection"), cleared by a successful fetch. It lets an asked check within the day give the could-not-check answer again without a new request.
- `newest`: the version file's three values from the last successful fetch (the version, its release date and whether it is important), replaced by each later successful fetch and validated again whenever it is read.
- `announced`, a list of at most 20 versions already announced (`ANNOUNCED_KEEP`), compared for equality. A "highest announced" value would let one false file claiming 9.9.9 silence every real later version.
- `highest_version_run`, merged by maximum. A computer with both the extension and a pip copy (for LM Studio) therefore never flips between versions or calls a downgrade an update. Nothing is written at start: it is written after a tool call once the state folder exists (`after_call`), or when the disclosure note or the after-update note is given (`mark_given`). It is not written while an after-update note is still to be given, so that note survives a restart that reached no answer.
- `disclosed_at` and `first_check_after`, for the disclosure note (3.5); the earliest disclosure on the computer stands.

**Concurrency.** One lock in the process (`_LOCK` in src/exegete/updates.py) guards every read-and-update. Each write re-reads the file under the lock and merges before replacing it atomically (maxima, unions, the earliest disclosure). The lock is the process's own: two copies writing in the same instant can lose one change, which at worst repeats a notice once. A second lock (`_FETCHING`) lets one fetch run at a time: a background check that finds one running gives up, and an asked check waits for it and uses its result. What this run set is also kept in memory (`_run.memory`), so the weekly limit and the once-per-version notice hold for the run even when the file cannot be written (a full disk, a Windows sharing violation). Several hosts can run Exegete on one computer; the MRU code was fixed for the same case (src/exegete/server.py, `_open_mru_tmp`: QA round 1, F20).

### 3.5 The notes Exegete gives once

**How they are delivered.**
- Every Exegete tool returns structured output. With mcp 1.30.0 a block appended as separate text reaches `content` but not `structuredContent`.
- Codex reads only `structuredContent` when it is present (openai/codex, codex-rs/protocol/src/models.rs, read 2026-10-04).
- The repository's own clients parse the joined text as JSON: scripts/smoke_desktop_extension.py (the `call` helper inside `ask`) and tests/test_v014_server_wide.py (`text_of` and `host_json`).
- So the note goes in as a top-level field, `exegete_notice`, inside the tool's JSON answer. The `call_tool` override (src/exegete/server.py, `_ExegeteMCP.call_tool`) first refuses an unknown argument as before, then asks `updates.due_note` whether a note is due; check_for_updates' own answers never carry one. With no note due, it calls `super().call_tool` unchanged. With one due:
  1. it gets the raw string from `self._tool_manager.call_tool(name, arguments, context=self.get_context(), convert_result=False)`, since `FastMCP.call_tool` always converts (mcp 1.30.0, fastmcp/server.py:359-362); the keyword exists back to mcp 1.17, the floor;
  2. `updates.attach` adds the field as the answer's last field, keeping the tool's own text byte for byte up to its closing brace, and checks that the result parses to the same object plus the note. It adds nothing to an answer that is not a JSON object, has an `error` key or already has the field; the note then waits for the next answer. The note is recorded as given (`updates.mark_given`) only once it is attached;
  3. `tool.fn_metadata.convert_result(raw)` converts it back, as the refusal of an unknown argument already does.
- It then reaches both `content` and `structuredContent` (whose `result` is the same JSON text: every tool's output schema is one string field).
- It is never added to a refusal: not to the refusal of an unknown argument, not to a tool's own refusal (an answer with an `error` key), and not to an error raised by argument validation; the note then waits for the next successful answer. It is never added to check_for_updates' own answer either: that tool says these things itself.
- Nothing about the check can fail a tool: an error in `due_note`, `attach` or `mark_given` is logged by its kind only and read as no note. `updates.after_call()` runs in a `finally` after every call except the refusal of an unknown argument.
- This differs from the existing once-per-run note (`EARLIER_WORKSPACE_NOTE` and `_earlier_workspace_note` in src/exegete/server.py), which two tools add themselves.

**When.** The server cannot tell conversations apart: Claude Desktop keeps one server for every conversation until it is quit. So "once" means the first successful tool answer after a note becomes due, in whichever conversation that is. One note at most goes with each answer, in this order: the disclosure note, the after-update note, the new-version notice. A server left running for a week also starts its weekly check from here, when a tool is next called (3.3). The record that a note was given is kept under the lock: `disclosed_at` (with `first_check_after`) for the disclosure note, the `announced` list for a new-version notice, and `highest_version_run`, raised to the installed version, for the after-update note. The run also keeps them in memory (`_run.given`, `_run.memory`), so no note is repeated in this run when the file cannot be written.

**The notes (wording A4 to A6):**
1. **The disclosure note** (D20: kept). It is due from the first start with the setting on, on either route, while no copy on the computer has recorded `disclosed_at`, and goes with the next successful tool answer. If check_for_updates is the first tool asked, its own answer says it instead and records it. On the Terminal route, where the check is off unless switched on, that is the first start after someone switches it on. It says what the check does, that it is on, that the first check is on or after a date seven days away (the date on the computer's own clock), and how to switch it off. It also says that nothing from the projects is sent, that GitHub records the computer's internet address and the time, and that PRIVACY.md, "Checking for new versions", says exactly what is sent. The first check waits seven days from the moment the note is given (`FIRST_CHECK_WAIT`). It is given whether the installation is new or an update, so 0.14.1 users are told too. An extension user who switched the setting off before the first start gets no disclosure, since nothing will connect.
2. **The new-version notice.** Once per version, as above: only with the setting on, after a check has found a version newer than the one installed, and not when that version is already in `announced`. When check_for_updates reports a newer version, that version is recorded as announced, so the notice does not repeat what the tool said. An important release gets its own fixed words (wording A5).
3. **The after-update note** (D19: kept). Given when the installed version is greater than `highest_version_run`. It is not given when nothing is recorded and no state folder exists, which means a genuinely new installation. When the state folder exists but holds no `update_check.json` (an update from 0.14.1 or earlier), the disclosure note takes its place if the setting is on, since it says what is new that matters most; if the setting is off, the after-update note is given. A state file whose record is missing or unreadable is read as no update, so no after-update note is given. Whether the state folder exists, and whether it holds `update_check.json`, is tested at start (`updates.start`, called from `main()` just after `_settle_state_folder()`). `start` itself writes nothing; only a weekly check it starts in the background records its attempt.

There are no other notes: no reminder when checking is off, and none when it keeps failing (D4, decided 5 October 2026). A copy that cannot tell its own version (a source tree never installed reports 0.0.0+unknown) gives no note and checks nothing on its own.

**Where the built-in text comes from.** The installed version's number, release date and summary are constants in `src/exegete/release.py` (`VERSION`, `RELEASED`, `SUMMARY`), set when each release is prepared. At 23404b9 they still describe 0.14.1-alpha; the next release's words are written when it is prepared. Tests (tests/test_updates.py, `TestTheRelease`) pin `VERSION` to pyproject.toml's version and `RELEASED` to the CHANGELOG heading `## [VERSION] - RELEASED`, and check that `SUMMARY` passes `forbidden_display_char` (src/exegete/database.py), is printable, is at most 300 characters and holds no link. A check in the release job is planned with the CI release jobs (D8, section 4.2), which are not built yet. The summary is the only free text Exegete shows about a version. It appears only in the after-update note, and the date only in check_for_updates' answer (`installed_released`), each only when the running version is the one release.py names.

**In the `core` tool set** the check tool is absent, so the new-version notice says "To update, see" the update page (`updates.UPDATE_PAGE`, not yet published) instead of the question to ask, and the disclosure note leaves out "and when they ask". The hook tells by whether check_for_updates is registered.

### 3.6 The "Is Exegete up to date?" tool

- **Name and tool sets:** `check_for_updates` (D9), an `async` tool with no arguments (src/exegete/server.py). It is placed in `full` and `lifecycle`, not `core` (D5). A newly decorated tool already lands there: `core` keeps only the tools in `CORE_TOOLSET`, and `lifecycle` adds `create_project` to the full set (server.py, `CORE_TOOLSET` and `_apply_toolset`). So `full` now has 74 tools, `lifecycle` 75, and `core` still 21 (tests/test_toolset_modes.py; tests/test_updates.py, `test_not_in_core`).
- **Annotations:** `TOOL_CHECKS_ONLINE` (server.py): not read-only, not destructive, idempotent, and `openWorldHint: true`, the only tool with it (tests/test_v014_server_wide.py, `EXPECTED_HINTS` and `test_one_tool_alone_claims_the_open_world`). Not read-only (D11): it may write the state file. In the hosts' asking modes, that means the researcher is asked before it runs. In auto modes, a classifier (Claude Code) or an automatic reviewer (Codex's "Approve for me") decides instead, as for Exegete's writing tools, and "Always allow" or a skip-all mode runs it unasked (INSTALL.md, "What hosts do with the tools' read and write marks"; server.py, the comment above `TOOL_READS` and the one above `TOOL_CHECKS_ONLINE`). Under Codex's own default for a server, `auto`, a tool that is neither read-only nor destructive is asked about when it claims the open world, so Codex asks before this one runs (INSTALL.md's Codex paragraph; tests/test_v0141_intro_openai.py, `codex_asks`, which models Codex's rule). A read-only mark would let it run unasked in more modes.
- **Fetching:**
  - `async def`, with the fetch in a worker thread under the overall deadline (3.3), so it never blocks the event loop;
  - when an attempt was made in the last 24 hours, its result is reused: a failed attempt gives the could-not-check answer again without a new request. So the tool contacts GitHub at most once a day;
  - only one fetch runs at a time in a process (`updates._FETCHING`): a check in the background that finds one running gives up, and the tool, asked while one is running, waits for it (at most `DEADLINE` plus two seconds, ten seconds in all) and uses its result instead of fetching again;
  - if the state file cannot be written (a full disk, a Windows sharing violation), what this run set is kept in memory (`_Run.memory`, read through `updates._current_state`), so the once-a-day and once-a-week limits and the once-per-version notice still hold until the server stops;
  - it honours the disclosure gate: if no disclosure has been recorded, its answer begins with the disclosure, addressed to the researcher (what is fetched, what GitHub records, how to switch it off), and records it, so the seven days start then; before the first-check date it makes no connection and says when the first check will be (wording A3.11). When the installed version cannot be told (a copy run from a source tree that was not installed), it makes no connection and says it cannot compare (updates.py, `tool_answer`).
- **With the setting off,** it connects to nothing and answers with the installed version, its date (given only when release.py describes the installed version), the update page, and how to switch checking on: the extension's setting "Tell me when a new version is out", or, on every other route, `EXEGETE_UPDATE_CHECK`, with INSTALL.md's "Environment variables the server reads" (D2; wording A3.9). Its `checking` field is `off`.
- **With the notes:** the hook adds no note to this tool's own answer (server.py, `_ExegeteMCP.call_tool`): the tool gives the disclosure itself, and when it reports a newer version, that version counts as announced, so the notice is not given again (updates.py, `tool_answer`). An after-update note still due waits for the next answer from another tool.
- **Its answer fields**, as JSON:
  - `message`: a short paragraph to pass on;
  - `steps`: a list of sentences in order, with no numbers in them (the tool's description calls them numbered steps). There are three on every route that gets any: for the extension, download, install, then quit and reopen Claude Desktop; for the Terminal routes, quit the app, the command, then open the app again. The list is empty when there is nothing to do or no safe command;
  - `installed_version` and `installed_released`;
  - `installed_as`;
  - `checking`, `on` or `off`;
  - `newest_version`, `newest_released`, `important` and `up_to_date`;
  - `download_link` (the extension route only), `release_notes` and `instructions_page`, the update page's address (https://nicotem.github.io/exegete/update/, not yet published). Section 11 records why the field is not called `update_page`.

  Dates are written as "20 September 2026", versions in the project's display form ("0.15.0-alpha"), and `installed_as` in words ("the Claude Desktop extension"); `installed_released` is given only when release.py describes the installed version, and is null otherwise.
- **Paths in its steps** are written from the home folder as `"$HOME/..."` for Terminal and `& "$HOME\..."` for PowerShell, so the account name stays out of the conversation. Both shells expand `$HOME` inside double quotes; neither expands `~` there, and PowerShell never expands `%USERPROFILE%`. This follows INSTALL.md's own `$HOME\exegete-venv\Scripts\pip` (pinned by tests/test_v0141_intro_openai.py, `test_updating_covers_the_terminal_route`). A path that holds a quote (straight or curly), a backtick or `$`, or (for Terminal) `!` or `\`, or a character that is not printable or that `forbidden_display_char` flags, gets no command (updates.py, `shell_path`). Under the home folder the check covers the part after `$HOME`; a path outside the home folder is written as it is, with the same checks over the whole path. With no command, the answer points to the update page and INSTALL.md, "Updating the MCP Server" (wording A3.7); a copy started under the old name is pointed to INSTALL.md, "Coming from qualcoder-mcp", instead.
- **One shell.** Each command step is given for this computer's own shell only (updates.py, `_Run.windows`, from `os.name`): the PowerShell form on Windows, the Terminal form elsewhere, and the step names the shell ("In PowerShell, run: ..." or "In Terminal, run: ..."). The extension's quit step likewise gives the Windows instructions on Windows and the Mac ones elsewhere.
- **The feasibility study of 2 October 2026 (not in the repository) recommended against an MCP tool.** The owner's approval of layer 1 on 4 October 2026 overrides that. What it cost in the build:
  - 13 existing test files changed: nine for the tool counts (73 to 74 for `full`, 74 to 75 for `lifecycle`; tests/test_toolset_modes.py also for the measurements, and tests/test_v012_session_id_removed.py to await the one tool that is `async`), and four others: tests/test_v014_server_wide.py (the hints table, the open-world test, the every-tool run), tests/test_v014_desktop_extension.py (the extension's settings, environment and documented variables), tests/test_v0141_compat.py (the extension's environment) and tests/test_v0141_intro_openai.py (a renamed README heading); also the new tests/test_updates.py and, in tests/conftest.py, a network guard for the whole suite;

### 3.7 The setting, and knowing how Exegete was installed

**`EXEGETE_UPDATE_CHECK`** (in `names.NEW_ONLY_SETTINGS`, read by `env_settings.update_check`; `updates.read_setting` says what each value means):
- `on`, `true` and `1` mean on; `off`, `false` and `0` mean off, in any letter case.
- Unset, empty, only spaces, or any value that begins `${` once spaces are stripped (an unsubstituted `${user_config...}`) means the route's default (D1): on for the extension, off for every other route.
- Any other value means off, with one warning in the log.
- It never stops the server. The project's two existing rules disagree here. Stopping the server on a bad value is the project's rule for the tool set; the existing switches treat anything but `1` as off. The security and consistency reviews pointed out that a setting which stops the server would, if Claude Desktop passed an unexpected value, stop Exegete for every extension user who updates, and a server that does not start can never announce the fix.
- Nor does any other failure of the check: `updates.start` is guarded in `main`, so a failure there is logged and the server starts without the check, and a failure in the answer hook is logged and the tool's answer goes out without a note (server.py, `main` and `_ExegeteMCP.call_tool`; tests/test_updates.py, `test_a_start_that_fails_never_stops_the_server` and `test_a_failing_check_never_fails_a_tool`).

**The extension:**
- a third `user_config` entry, `update_check`, of type `boolean`, which the MCPB spec shows as a "Checkbox/toggle": titled "Tell me when a new version is out", on by default, with a description that says what it sends (packaging/desktop-extension/manifest.in.json);
- the manifest passes `"EXEGETE_UPDATE_CHECK": "${user_config.update_check}"` and the marker `"EXEGETE_INSTALLED_AS": "extension"`. The repository's model of Claude Desktop turns a boolean into "true" or "false" (scripts/smoke_desktop_extension.py, `launch_config`), still to be checked on a real computer (section 13, item 1).

**The settings tables:**
- `names.SETTINGS` holds only new/old pairs, and a test pins it as six (tests/test_v0141_compat.py, `test_the_table_is_six_pairs_with_the_new_prefix`). The new entries have no old spelling, so they were kept out of it, in a table of their own, `names.NEW_ONLY_SETTINGS`, and `names.SETTINGS` is unchanged. The reshape this design proposed was not made: the pairs end at v1.0, and keeping the new-only settings apart leaves `SETTINGS` to be removed then without touching them (names.py, the comment above `NEW_ONLY_SETTINGS`).
- Since the pairs are unchanged, nothing that reads them changed. The places that list every setting were extended: two readers, `env_settings.update_check` and `env_settings.installed_as`; the extension's environment, now eight entries (tests/test_v0141_compat.py, `test_the_six_entries_and_their_equality`; tests/test_v014_desktop_extension.py, `test_each_setting_reaches_a_variable_the_server_reads`); INSTALL.md, "Environment variables the server reads", whose paragraph on earlier spellings now says the two have one spelling only; and the test sandbox, which clears them (tests/conftest.py, `_isolate_home`).

- runs only for a release (`kind=release` from scripts/release_version.py), never for a rehearsal or a `.devN` early build; since immutable releases were chosen (D13), build-extension and attach-extension will start from `workflow_dispatch` on a draft release, and announce from the existing `release: published` (see below);
- has its own permissions block and `timeout-minutes`;
- uses only SHA-pinned actions recorded in VERIFIED_TAGS.

1. **build-extension** (`contents: read`; 20 min)
   - Check out with `persist-credentials: false`.
   - Build the `.mcpb` twice from the tag and compare the two, as ci.yml's `desktop-extension` job does (its step "Build the extension twice from this commit", which builds twice from the commit and compares the two with `cmp`).
   - Read the version, date and summary from the committed `release.py` (`VERSION`, `RELEASED`, `SUMMARY`; tests/test_updates.py, `TestTheRelease`, already holds them to pyproject.toml, the CHANGELOG heading and the character rule on every CI run), and check that `VERSION` matches the tag.
   - Write `latest.json` with `"format": 1` (the integer), `version` in its PEP 440 form (0.15.0a0, not `release.VERSION`'s 0.15.0-alpha), `released` no later than the day of the deploy (a copy refuses a date more than two days after its own UTC date), and `important` as a JSON boolean: any other value makes every copy refuse the whole file (`updates.parse_version_file`). `release.py` has no `important`; it is to be added there, or taken as the job's input, when the jobs are written.
   - Upload the `.mcpb`, its SHA-256 and `latest.json` as an artifact, and output the SHA-256.
2. **attach-extension** (needs build-extension; `contents: write`, `id-token: write`, `attestations: write`; an environment `release` limited to `v*` tags; 10 min)
   - No checkout and no package installs.
   - Check the SHA-256.
   - Attest the build (`actions/attest-build-provenance`), so that an IT team can run `gh attestation verify exegete.mcpb -R nicotem/exegete`.
   - Upload both file names with `gh release upload`, the tag passed through the environment, never inside the command.
3. **announce** (needs publish-to-pypi, and checks that attach-extension's files are attached, see below; `pages: write`, `id-token: write`; the `github-pages` environment limited to `v*` tags, with **the owner as required reviewer**; 10 min)
   - Refuse unless the new version is greater than the one in the live `latest.json` (`updates.VERSION_FILE_URL`); for the first deploy no file is live yet, so the job must allow for a missing one.
   - Deploy with `actions/upload-pages-artifact` and `actions/deploy-pages`. A deploy replaces the whole site, so the artifact must carry the update page (at `/update/`, `updates.UPDATE_PAGE`) as well as `latest.json`. Where the page's source lives, and which job builds it, is still to be decided.
   - Fetch the live file afterwards, and fail if it differs.
   - The owner's approval is the last step of each release, and also a hold switch for a bad one.

Under D13 the plan needs three changes when the jobs are written. The run that builds and attaches must be told apart from publish.yml's TestPyPI rehearsal, which also runs on `workflow_dispatch` (publish-to-testpypi, and the step "Practice version (manual runs only)", which rewrites the version): for example a workflow of its own, or an input the rehearsal's jobs check. Its tag input must go through scripts/release_version.py, which today runs only on `release`. And announce, in the later `release: published` run, cannot `need` attach-extension from the earlier run: it needs publish-to-pypi, checks itself that both assets are attached, and either fetches `latest.json` from the earlier run's artifact or writes it itself.

**Rules around the jobs:**
- **Pages** is to be deployed from GitHub Actions (D3), never from a branch: a branch would let any token with `contents: write` rewrite `latest.json` without a release. Pages is not set up yet.
- **A ruleset** is to protect `v*` tags (not set up yet).
- **The test ledgers** need entries for the new jobs and actions: WORKFLOW_JOBS, VERIFIED_TAGS and the SHA pins (tests/test_v012_workflow_pins.py), and the CHANGELOG's "### CI" entry, which must name each pinned action and version (`test_changelog_ci_entry_names_the_pinned_versions`). They also need time limits: publish.yml has no `timeout-minutes` today, and the time-limit test (tests/test_v014_workbench.py, `JOB_TIME_LIMITS`) reads ci.yml only.

**Immutable releases (D13, decided 5 October 2026: yes; not yet switched on).** Once a release is published, attaching assets is refused (to be confirmed, section 13, item 13), and GitHub starts no workflow for a draft release. So build-extension and attach-extension will run on `workflow_dispatch`, with the tag as input and the release still a draft; the owner checks and publishes it; then `release: published` starts the PyPI upload and, after it, the announce job.

## 7. Security summary

- **Notify only.** Nothing is downloaded or run automatically. The researcher always installs through Claude Desktop's own screen, or types the command themselves.
- **Never a reason to fail.** Every network and parsing problem ends as "could not check", with one log line naming only its kind. A state file that cannot be read counts as empty; one that cannot be written is logged by kind, and the run's own memory keeps the limits. A failure at start or in the answer hook is logged, and never stops the server or a tool's answer (src/exegete/server.py, `main` and `_ExegeteMCP.call_tool`).
- **No network text and no network links enter the conversation** (3.1). Every link Exegete shows is written in src/exegete/updates.py from constants and the validated version, in one of five forms: the download link (`download_link`), the release-notes link (`release_notes_link`), the update page (`UPDATE_PAGE`), and two named sections of INSTALL.md on github.com/nicotem/exegete (`INSTALL_UPDATING`, `INSTALL_COMING_FROM`). A test checks that every link in the disclosure note and in the tool's answers for the extension and for the old name fullmatches one of them (tests/test_updates.py, `test_every_link_shown_is_one_of_exegetes_own`). The after-update note's link is pinned separately (`test_after_an_update_once`). The new-version notice and the answers for the other routes (pip, pipx, uv tool, uvx, a copy of the source, and a route Exegete cannot tell) are not in that test.
- **Strict validation** of the version file's four values (3.2), which also guards the pasted commands. The paths in those commands (the Python that runs Exegete, a git copy's folder) are written from `$HOME` when they lie in the home folder, so the account name stays out of the conversation. A path that holds a character no quoting can carry safely gets no command, only the update page and INSTALL.md. These characters are a straight or curly quote (PowerShell reads curly ones as quotes), `$` or a backtick, for Terminal also `!` or a backslash, and any unprintable character, bidirectional controls included (`updates.shell_path`; 3.6).
- **Fetch hardening (3.3):** https only (plain http only to this computer, for the tests), with no user name or password in the address; one overall deadline of 8 seconds; no redirects; verified TLS; any Content-Encoding other than identity refused; an answer over 16,384 bytes refused; strictly parsed input; `User-Agent: Exegete` as the only header it sets (the library adds only Host, Connection and `Accept-Encoding: identity`); and one fetch at a time in a process.
- **State written safely (3.4):** never before the state folder is settled, and nothing is written at start: the first write follows a tool's answer, a note given or a check. Each write is atomic (a temporary file made exclusively and owner-only, then a replace) and happens under this process's lock. It re-reads the file and merges what another copy wrote. Two copies writing in the same instant can lose one change, which at worst repeats a notice once. Every value is checked again when it is read. If the file cannot be written, an in-memory copy keeps the once-a-week limit and the once-per-version notice for the run.
- **Off means no connection.** Switched off, Exegete makes no connection at all, even when asked (`updates.tool_answer`). Switched on, the disclosure note comes first, and the first check waits at least seven days after it.
- **The tool's marks.** `check_for_updates` is the only tool with `openWorldHint` true. It is not marked read-only, so hosts that ask before a tool runs ask before it (src/exegete/server.py, `TOOL_CHECKS_ONLINE`). It is not in `core`.
- **CI (planned, not built yet; D8, 4.2):** three release jobs in publish.yml, to keep the write token away from any job that runs third-party code, to attest the build, and to announce last, behind the owner's approval. nicotem/exegete#11 does not change publish.yml, so `latest.json` and the update page are not published yet.
- **Standing rules on names and domains** (4.5), also in CONTRIBUTING.md, "The check for new versions": never rename or delete the nicotem account, the exegete repository or its Pages site, and never set a custom domain on this Pages site or on the account's own one.

## 8. Tests

- **The check:**
  - a local version-file server on 127.0.0.1 that each test starts (tests/test_updates.py, `Site` and the `site` fixture), reached by pointing `updates.VERSION_FILE_URL` at it; the fetch tests that need another address or a shorter deadline pass them to `fetch()`. No fetch function is injected, and no server listens on ::1;
  - cases: newer, same and older versions; .devN; unknown installed versions; every malformed form in 3.2; redirects; slow bodies; oversized answers; NaN; duplicate keys; deep nesting; a non-UTF-8 body; a compressed answer; an error page; nothing listening; plain http beyond this computer, ftp, file and a user name and password in the address; and the request's headers (User-Agent: Exegete, no cookie, and nothing beyond what the library adds);
  - the seven-day limit, the 24-hour reuse, the disclosure gate and the `announced` list;
  - the state file (written atomically and owner-only, anything malformed treated as absent, merges keeping the highest and the earliest); the setting (an unrecognised value is off and logged, never a stop) and the route; and the review's findings (tests/test_updates.py, `TestRestartsAndFailures`): an after-update note not yet given survives a restart, a first session or a corrupt record is never taken for an update, a start writes nothing, unwritable state still checks once a week, an asked check waits for a running one, a git copy started under the old name is taken for a git copy, and a git copy's steps stay on its branch;
  - the setting off: the tool answers without any request reaching the test server, and on a fresh computer a start gives no note and creates nothing (`test_off_makes_no_connection`, `test_off_on_a_fresh_computer_says_nothing_and_makes_nothing`). That no name is looked up follows from the code (`updates.tool_answer` returns before any fetch); no test observes it.
- **The address override** is a module attribute, `updates.VERSION_FILE_URL`, as `_MRU_FILE` is (src/exegete/server.py, `_MRU_FILE`). An autouse fixture in tests/conftest.py (`_isolate_update_check`) points it, for every test, at a port on this computer where nothing listens (http://127.0.0.1:9/latest.json), so a check that a test starts fails at once, and locally. The `site` fixture in tests/test_updates.py points it at that test's own server, and a test pins the real address in the source (`test_the_real_address_is_https_on_the_project_site`). No environment variable is read for it: a new one would have to go through env_settings and be documented (tests/test_v0141_compat.py, `TestNoOtherEnvironmentRead`; tests/test_v014_desktop_extension.py, `test_install_documents_every_variable_the_server_reads`, which now also requires `EXEGETE_UPDATE_CHECK` and `EXEGETE_INSTALLED_AS`).
- **A network guard** runs in the pytest process only: a session-wide autouse fixture in tests/conftest.py (`_no_test_reaches_the_network`) replaces `socket.getaddrinfo`, `socket.socket.connect` and `connect_ex`, and allows only localhost, 127.x and ::1. Servers the suite starts as subprocesses do not inherit it. They reach nothing because the check is off on the Terminal route unless switched on (tests/conftest.py removes `EXEGETE_UPDATE_CHECK` and `EXEGETE_INSTALLED_AS`), and when it is on, nothing connects before the first-check date, at least seven days after the disclosure. ### 9.1 Size, and the context window

**How the tool set meets the context window.** Every time the assistant takes a turn, the host sends the model the definition of every tool switched on: its name, its description and the description of its arguments. They sit in the context window for the whole conversation, whether or not they are used. The release notes publish this figure: "the descriptions a host is sent with every request" (195,266 characters in `full` on Python 3.13.5; the project's rule of thumb is about four characters to a token). With the check, the figure is 195,975 characters in `full` on Python 3.13.14 (CHANGELOG.md, "[Unreleased]", "Measured"; TOOLS.md and INSTALL.md round it to about 196,000, and `lifecycle` to about 199,000).

**Measured, not estimated.** The feature is measured with the project's own method (tests/test_toolset_modes.py, `TestThePublishedSchemaBudget._measure`: name, description and input schema of every tool, serialised with `json.dumps`). The measurement was taken on Python 3.13.14 and 3.11.15 with mcp 1.30.0, in environments built from `uv.lock` (`uv sync --frozen --extra dev`). On 0.14.1's tree the same environments give 0.14.1's published figures exactly (195,266, 64,804 and 197,845, published for 3.13.5; 204,974, 68,096 and 207,693, published for 3.11.13), so the deltas below are on the same footing. CHANGELOG.md, "[Unreleased]", "Measured", publishes the new figures. tests/test_toolset_modes.py, `TestThePublishedSchemaBudget`, pins the 3.13 ones exactly (`FULL_MEASURED` = 195,975, `CORE_MEASURED` = 64,804, `LIFECYCLE_MEASURED` = 198,554) and holds Python 3.10 to 3.12 within two per cent of the 3.11 ones (205,683, 68,096, 208,402).

| Tool set | 0.14.1 (Python 3.13; 3.11) | With `check_for_updates` (Python 3.13; 3.11) | Added |
|---|---|---|---|
| `core` (21 tools, unchanged) | 64,804; 68,096 | 64,804; 68,096 | 0 (the tool is not in `core`, D5) |
| `full` (73 tools, then 74) | 195,266; 204,974 | 195,975; 205,683 | +709 characters (+0.36%; +0.35%), about 180 tokens |
| `lifecycle` (74 tools, then 75) | 197,845; 207,693 | 198,554; 208,402 | +709 characters (+0.36%; +0.34%) |

Counted with everything a host actually receives for a tool (its annotations and output schema too), the new entry is 981 characters, about 250 tokens, on both interpreters.

**For scale:**
- it is among the smallest of the 74 tools in `full` (the sixth smallest), since it takes no arguments; of the other 73, on Python 3.11.15, the smallest, `get_project_summary`, is 444 characters, the median 2,451 and the largest, `pseudonymise_source`, 20,487 (on 3.13.14: 424, 2,325 and 19,403);
- the whole feature costs about a twenty-ninth of `pseudonymise_source` alone on Python 3.11 (about a twenty-seventh on 3.13);
- its description, 536 characters, is far below the 2,048 characters at which Claude Code cuts a description; a test keeps it below that (tests/test_updates.py, `TestTheServer.test_the_tool_is_the_only_one_reaching_beyond`).

**Everything else is paid once, not with every turn:**

| What | Size | When it enters the context |
|---|---|---|
| Server instructions | unchanged | (never; nothing is added there) |
| The disclosure note (D20) | about 630 to 665 characters | once per computer, while checking is on, in one conversation (every copy on the computer shares its record) |
| The new-version notice | about 440 characters (about 465 for an important version) | once per new version, in one conversation |
| The after-update note (D19) | about 270 characters, plus the release's summary from release.py (about 380 with 0.14.1's) | once per update, in one conversation |
| The tool's answer | about 520 to 2,200 characters (about 520 to 550 when up to date; about 2,100 to 2,200 with the extension's three steps) | only when the researcher asks, in that conversation |

Each note also adds its field name, `"exegete_notice": `, to the answer that carries it.

A note stays in the history of the conversation it appeared in, like any tool answer, and enters no other conversation. A host that logs every answer, as Claude Desktop's server log does, logs it too.

**The `core` set**, which exists for local models with small context windows, gains no tool definition. Its only cost is those one-time notes.

**The smaller alternative, not taken.** With no new tool, the weekly check would still have run, and the one notice would have carried the update steps itself; "Is Exegete up to date?" would have been answered from an existing tool, using the last weekly result, with no fetch on request. That would have saved the 709 characters, but the existing tool's description would have grown a little, and layer 1 (approved on 4 October 2026) would have lost its fresh check on request. The tool was built, as layer 1 asked, since 0.36% of `full` (0.35% on Python 3.11) buys the clearest experience.

**The engineering size, as built.** The code part of step 3 took two new modules (src/exegete/updates.py, 1,269 lines; src/exegete/release.py, 21 lines); one tool; a separate table for the two new settings (`names.NEW_ONLY_SETTINGS`; `names.SETTINGS` is unchanged); changes to 13 existing test files, besides tests/conftest.py, which gained a suite-wide network guard; a new tests/test_updates.py (79 test functions); and the documents: 2,824 lines added over 29 files. The three CI jobs are still to do. The page is not yet made: its screenshots need a real Mac and a real Windows computer with Claude Desktop. The list and the reminders were dropped on 5 October 2026, before the build, so their two notes, one state field and the list's texts were never written.

## 11. Where the build departs from this design

nicotem/exegete#11 follows this design except as listed here. Each entry gives what was designed, what was built, and why; "no reason recorded" means that no commit message, code comment or test gives one. Work that is planned but not yet done (the CI release jobs, the second file name, the Pages site and page, the repository settings, the real-computer checks) is not a departure: sections 4, 9 and 13 list it.

1. **The field for the update page.** Designed: `update_page` (3.6). Built: `instructions_page`, beside a `checking` field (`on` or `off`) that the design did not list. Why: no reason recorded; most likely the end-to-end test that reads every answer (tests/test_v014_server_wide.py, `TOOL_SHAPED` and `NOT_TOOLS`) would take `update_page` for a tool that does not exist.
2. **Commands for this computer's shell only.** Designed: every command step in both Terminal and PowerShell forms, and the extension's quit step for a Mac and for Windows (3.6; wording A3). Built: one form, chosen by `os.name`: PowerShell on Windows, Terminal elsewhere, with the shell named in the step; the quit step gives the Windows or the Mac words only (`updates._Run.windows`). Why: no reason recorded beyond the comment "Commands, written for the shell of this computer"; Exegete runs on the computer being updated, so it knows its system.
3. **How the extension is recognised, and the route order.** Designed: the marker, with the Claude Desktop extension folder as fallback (D16); then the old name, pipx or uv tool, a copy of the source, uvx, and pip as the default (3.7). Built: the marker only; then a git copy under either name, the old name, uv tool, pipx, uvx, pip only in a virtual environment, and otherwise "unknown" with no command (`updates.detect_route`). Why: a git copy is updated as a git copy, under either name (commit 1448475, from the review of the build). No reason recorded for dropping the folder fallback (every extension package with the check sets the marker) or for limiting pip to a virtual environment. `detect_route`'s docstring gave the designed order until it was corrected on 6 October 2026.
4. **The old name.** Designed: both names pinned on every route (wording A3.6); at v1, steps for moving to `exegete` (sections 9 and 10). Built now, not at v1: both names pinned with the running Python's pip only in a plain virtual environment and while the newest version is below 1.0 (a copy started with `uvx qualcoder-mcp` counts as one, and gets a pip command for uvx's own cache); otherwise no command and no steps, only INSTALL.md, "Coming from qualcoder-mcp". A git copy under the old name gets the git steps. Why: the two-name forms for uv tool and pipx were never tried (the comment in `updates._terminal_steps`); the git copy, commit 1448475. No test covers a newest version of 1.0 or later here.
5. **The git steps.** Designed: `git fetch --tags`, `git checkout v<new>`, `pip install -e .` (3.7). Built: in the copy's folder, `git fetch --tags`, then `git merge --ff-only v<new>`, then `"<python>" -m pip install -e .`. Why: commit 1448475 says only that the git steps merge with `--ff-only`; the step's own words say the merge "stays on its branch, and refuses if the copy has changes of its own" (`updates._terminal_steps`; tests/test_updates.py, `test_a_git_copy_stays_on_its_branch`, which also checks that no checkout is given).
6. **The settings table.** Designed: `names.SETTINGS` reshaped to hold entries with no old spelling (3.7). Built: a separate table, `names.NEW_ONLY_SETTINGS`, read by `env_settings.update_check` and `env_settings.installed_as`; `names.SETTINGS` and its pins are unchanged. Why: the comment above the table: "kept apart from SETTINGS, whose pairs end at v1.0". (The same comment named a reader, `env_settings.new_only`, that does not exist, until it was corrected on 6 October 2026.)
7. **When the state is written.** Designed: the start tests the state folder before this run writes anything, and the record of a note given is the `announced` list or a timestamp (3.4, 3.5). Built: `updates.start` writes nothing. The version that runs is recorded after a tool call once the state folder exists, or when the disclosure or after-update note is given, and never while an after-update note is due. An update from 0.14.1 is told by a state folder with no `update_check.json`; a corrupt record is read as none. Why: commit 1448475: the after-update note survives a restart, a first session is never taken for an update, and a start that is never used changes nothing.
8. **State kept in memory, and one fetch at a time.** Designed: the limits kept in the state file under one lock (3.4). Built: what the run set is also kept in memory (`_Run.memory`), so the limits, the disclosure and the once-per-version notice hold when the file cannot be written; a second lock, `_FETCHING`, allows one fetch at a time, and an asked check waits for a running one (up to ten seconds) and uses its result. Why: commit 1448475: a full disk or a Windows sharing violation must not make the check run at every call or repeat a notice, and an asked check must not answer "no answer yet" while a background one runs.
9. **The hook and the check tool.** Designed: the override always takes the raw path, since it "cannot simply call `super()`", and a note goes with the next successful answer of any tool (3.5). Built: with no note due, the override calls `super().call_tool` unchanged, and it never adds a note to `check_for_updates`' answers: the tool says the disclosure itself and records it, and a newer version it reports counts as announced; an after-update note waits for another tool's answer. Start-up and the hook are guarded, so neither can stop the server or fail an answer. Why: the hook's comment, "check_for_updates says these things itself"; commit 1448475 for the guards. No reason recorded for leaving the after-update note out of the tool's answer.
10. **The log lines.** Designed: "checking for new versions: on" or "off", and failures in the `error_label` style (3.3). Built: "Checking for new versions: on" (or "off") at INFO level, after one warning for an unrecognised value; a failure logs one of eight fixed phrases, the same the tool's answer names. Why: the kind is the only thing about a failure that is logged or shown (`CheckFailed`'s docstring), so one set of words serves both.
11. **The first-check date.** Designed: the first check once the date the note names has passed (3.3). Built: a timestamp exactly seven days after the disclosure (`first_check_after`); the note names that day on the researcher's own clock, so the check may run on that day. Why: the gate has been a timestamp since the first commit; commit 1448475 made the named date local, not UTC.
12. **The installed version.** Designed: parsed by the same code as the published one; an unknown one gets no notice and no steps (3.2). Built: its own pattern, `_INSTALLED`, which also allows `.devN`; an unknown version gets no note of any kind and no check, and the tool says it cannot compare. Why: section 3.2 asks for both: the version file may not name a `.devN` build, but an installed one must rank below its release (tests/test_updates.py, `TestVersions.test_an_early_build_ranks_below_its_release`); `parse_installed`'s docstring adds that an unknown version is never "old".
13. **The fetch.** Designed: no plain http; no `Accept-Encoding` sent; a test pinning the exact headers and asserting `verify_mode` and `check_hostname` (3.3). Built: plain http only to this computer; the library's own `Accept-Encoding: identity`, accepted; a header test that checks a set, and a TLS test that checks only that the default context requires a certificate. Why: the tests serve the file from 127.0.0.1 (the comment in `_opener`); no reason recorded for the rest.
14. **Paths in commands.** Designed: a path with a quote, a backtick, `$`, or for Terminal `!` or `\`, or a character `forbidden_display_char` flags, gets no command, only the update page (3.6). Built: curly quotes and unprintable characters are refused too; a path outside the home folder is written in full; with no command, the answer also names INSTALL.md's section. Why: commit 1448475 (PowerShell reads curly quotes as quotes); the INSTALL link follows wording A3.7; no reason recorded for writing an outside path in full.
15. **The tests' network guard and address.** Designed: an injected fetch function; a test server on 127.0.0.1 and ::1; a guard in-process and, through a `sitecustomize`, in subprocess servers, which would also set the address; the smoke run with `update_check=false`; a stdout test with checking on (8). Built: each test starts a real server on 127.0.0.1 and points `updates.VERSION_FILE_URL` at it; the guard is a session-wide socket patch in tests/conftest.py, in the pytest process only; every other test's address is a closed local port; the smoke script is unchanged and runs with checking on; no stdout test. Why: the guard's docstring: subprocess servers "check nothing unless a test switches the check on, and even then not before the week the disclosure note promises has passed", which holds for the smoke run too. No reason recorded for the rest.
16. **The link test and the second copy.** Designed: every link shown tested against four forms; notes never given twice across two processes (7, 8). Built: five forms, applied to the disclosure note and to the tool's answers for the extension and the old name; the second copy is simulated in one process (`updates.reset_for_tests`). Why: no reason recorded.
17. **Sizes.** Designed: re-measured on Python 3.13.5 and 3.11.13 in the repository's own `venv/` and `.venv/`; notes of about 660, 390 and 250 characters (8, 9.1). Built: measured on Python 3.13.14 and 3.11.15 with mcp 1.30.0 in environments built from `uv.lock`: full 195,975, core 64,804, lifecycle 198,554 on 3.13; 205,683, 68,096, 208,402 on 3.11; the tool adds 709 characters to full and lifecycle. The notes are about 630 to 665, 440 and 270 characters (the last plus the summary). Why: those environments give 0.14.1's published figures exactly on 0.14.1's tree (the comment in tests/test_toolset_modes.py); the note sizes were estimates made before the texts were written.
18. **The old setting names.** Designed: when the tool sees `QUALCODER_MCP_*` settings, its steps begin with renaming them (10). ## 13. To verify on a real computer

None of these has been checked yet. The code was written first, in nicotem/exegete#11 (5 October 2026); items 1 to 6 must pass on a real Mac and a real Windows computer before a release carries the check (section 9, step 2). The items keep their numbers, since a checklist for the owner's own computer refers to them.

1. How Claude Desktop passes a `boolean` setting to the server. The repository's model says "true"/"false" (scripts/smoke_desktop_extension.py, `launch_config`). Exegete reads on, true and 1 as on and off, false and 0 as off, in any letter case; an empty or unreplaced value gives the route's default, and anything else turns the check off with one warning in the log (`updates.read_setting`). Confirm in the real app: with the box ticked the log reads "Checking for new versions: on", unticked "off", and no warning line appears.
2. Whether an update that adds the third setting gives existing installations its default. The model takes each setting's default from the manifest and lays the values given with `--set` over it (scripts/smoke_desktop_extension.py, `launch_config`); it keeps no saved values. If the app passes the setting empty or as an unreplaced `${user_config.update_check}`, Exegete uses the extension's default, on (`updates.read_setting`). Confirm.
3. Whether Claude passes on an `exegete_notice` field: in Claude Desktop's chat, in Codex and in Claude Code.
4. Whether Claude's installation screen shows optional settings.
5. Quitting Claude Desktop fully on Windows (tray icon, Quit or Exit; File, Exit; the time it takes), and whether a quit is needed at all after installing an update.
6. The install button's label when Exegete is already installed, and whether settings survive. CI's update runs (ci.yml, the smoke with `--over`) install the earlier package without starting it and start only the new one, with the manifest's defaults, so they cannot show that settings survive. The app's log line "preserving settings" is the only evidence (scripts/smoke_desktop_extension.py, the module docstring's paragraph on `--over`). The steps the tool gives say "Click Install" (`updates._extension_steps`), so the button's label matters too.
7. Windows app-package (MSIX) and .exe installs of Claude Desktop: opening a `.mcpb` by double-click, as the tool's steps say (`updates._extension_steps`), and where extensions live (for the rename's transition check, `transition.extension_folders`; the check for new versions knows the extension by its marker alone, D16).
8. The check behind a TLS-inspecting proxy, on a Mac and on Windows, with the uv-managed Python.
9. Whether Claude Desktop starts extensions when the app opens. If so, checks happen in weeks when Exegete is not used.
10. What Claude Desktop shows from `privacy_policies`.
11. That GitHub shows the site's owner no record of who fetched `latest.json`.
12. Whether the `github-pages` environment allows deploys from tags.
13. Whether immutable releases refuse assets after publication.
14. Whether the version is shown in Claude's Settings, Extensions, Exegete (the update page could then point to it).

Items 11 to 13 need the Pages site, the release jobs (D8) and the repository settings (D3, D13), none of which exists yet.
